## 三、问题诊断

### P1 · 治理随「人」走：巡检在交付日后停止

**现象**：设计中的 PM 治理是「定期轮询各 Agent 状态、更新里程碑、风险预警」（team-agent-design.md §3.1）。实际巡检 12 次全部集中在启动后的 8 天内，交付宣言（patrol-12）之后 141 天为零。

**根因**：巡检是一个**需要被外部触发的行为**，触发源是「人类开着会话让 PM 跑」。项目兴奋期一过，会话不再开启，治理瞬时归零。没有任何机制（cron、CI、hook）在巡检缺席时报警。

**影响**：所有依赖巡检闭环的承诺随之悬空。doc-sync-policy.md:119 写明「PM 在**下次巡检**时确认各层设计文档已更新至 v1.1+」——那次巡检永远没有发生，六份设计文档至今一份 v1.0、五份停留在「设计中」（见 P7）。

### P2 · 「唯一数据源」失守：注册表与 git 历史脱节

**现象**：task-registry.yaml 自称「唯一数据源」（plan.md §相关文档），52 个任务里 47 个 completed 于 2026-04，5 个（T-060..T-064）补录于 2026-08-29。而注册表在 04-13（`5798e70`）之后直至 08-29（`1c5c3d2`）之间**零更新**——这 4.5 个月里合并了 13 个 PR，全部发生在注册表视野之外。

**根因**：注册表靠 PM 手工同步；维护期改走 GitHub PR 流后，没有任何桥接（hook/CI/action）把 PR 事件写回注册表。数据源一旦与真实工作流（git）分离，就必然漂移。

**影响**：以注册表为准，「项目在 4 月就完成了」；以 git 为准，4 月之后还有 19 次实质合并/提交、约 10K 行增量代码。两套账本并存，事后只能靠 git 取证重建事实（本文档即是一次）。T-060..T-064 是事后补录进注册表的，恰好证明了「先做事、后补账」已成为常态。

### P3 · DoD 在系统内部闭合：与原版的行为对齐从未进入验收

**现象**：项目目标写的是「全量重写 Claude Code（TS → Go），模块设计完全不变」（team-agent-design.md §一）。而 M3 完成标准（plan.md §M3）是：`go test -race` 通过、`go build` 出二进制、验收报告出具。两者之间没有桥。交付日非测试代码 16,322 LOC，约为原版 512K+ LOC 的 3.2%。

**证据**（交付状态与「全量交付」宣言并存）：

- 80 个 `TODO(dep)` 占位（M2 明确承诺「补全所有 TODO」，该承诺从未兑现，也从未产生任何一个回填任务）；
- 至今仍有 42 处 `not yet implemented` 桩直接面向用户返回 `IsError: true`——分布：`bootstrap/plugin.go`×8、`bootstrap/mcp.go`×7、`bootstrap/misc.go`×6、`tools/misc/`×5、`tools/interact/worktree.go`×4、`commands/builtins.go`×4、`tools/mcp/`×3 等；
- DoD 清单（team-agent-design.md §6.4）六项全部是**内部工件**：测试覆盖率、评审通过、验收通过、文档更新、PM 标记完成。没有任何一项要求「与原版行为对比」。

**根因**：验收信号的闭环在流程内部（Agent 产出 → 同族 LLM 评审 → 同族 LLM 验收），没有一个外部锚点（原版可执行文件的行为、真实使用场景）参与判定「重写是否成立」。

**影响**：「26/26 包 PASS、69.4% 覆盖率」在字面上为真，但它度量的是**这 3.2% 代码自身的质量**，不是「Claude Code Go 版」这个产品目标的达成度。覆盖率高分反而延迟了对缺口的感知。

### P4 · 三道门在关键场合被整体绕过

**现象**：设计中的门禁是「设计评审 → 代码评审 → QA 验收」，且 main 只收经 Tech Lead 评审的 PR（team-agent-design.md §四）。2026-08-29 的 `1c5c3d2`（feat: close permission system gaps T-060..T-064）**同时绕过了全部三道门**：无 PR、无 TL 评审、无 QA 报告，直接落在 main 上（随后被 `207259c` 以本地 merge 包裹），规模为 43 文件、+2,299/−211，横跨 permissions/tools/tui 等多个包。

**根因**：门禁是流程约定，不是技术强制——main 分支没有保护，`git push` 直接可达。当变更者同时是流程的制定语境（CLAUDE.md 把所有会话统一注入为 PM Agent 身份，`d425ee9`）时，「PM 不得直推 main」的 Forbidden Action 约束不了任何一次真实的手指动作。

**影响**：这恰好是一个**跨 5 个包的权限系统变更**——即原流程声称最难、最需要评审的那类工作（见 P5），却以最不设防的方式落地。事后 `f03a3ff` 的「docs: refresh project docs to 2026-08-29 reality」对文档做了对齐性追改，属于先违规、后修账。

### P5 · 分层并行在跨层变更上成本反转

**现象**：构建期按架构分层的 6 Agent 划分，在维护期暴露出反向成本：真正常见的维护需求（一个功能缺口往往横切 permissions → tools → tui）在分层模型下需要多 Agent 协调 + PM 仲裁。实际结果：T-060..T-064 由**单一提交者一次直推**完成——绕开流程比走流程便宜得多时，流程就会被绕开。

**根因**：分层是**建设期**的最优分割（界面清晰、可并行），但**维护期**的自然分割是「按变更主题」而非「按层」。流程没有随阶段切换而重构，于是被弃用而非被修改。

**影响**：维护期事实上形成了一套未成文的新流程（gap 文档 → feat 分支 → PR），而旧流程的全部文档、注册表、角色定义仍以「现行制度」的身份留在仓库里，误导后续会话（见 P8）。

### P6 · TODO(dep) 回填依赖一个无状态的协调者

**现象**：并行启动策略要求「依赖未就绪时 TODO 标记继续推进，PM 跟踪依赖链，就绪即通知回填」（team-agent-design.md §五）。实际：交付日留下 80 个 TODO(dep)，承诺回填的 M2 已宣告完成；此后没有任何任务、任何巡检、任何机制以回填为目标。4.5 个月后仍有 56 个。

**根因**：回填需要**跨会话的持久记忆 + 主动触发**。PM Agent 无状态，每次会话冷启动；巡检停止后，「谁记得有 80 个欠账」的答案是「没有人，只有 grep」。

**影响**：TODO(dep) 从「临时并行手段」沉淀为**永久桩**。用户可见的行为缺口（工具返回 not-implemented 错误）与「已交付」的项目叙事长期并存。

### P7 · 文档/代码倒挂，与事后追认

**现象**：docs/ 72 个文件 1.4MB，对 27K LOC 的代码；六份分层设计文档一份 v1.0、五份「设计中」，低于 doc-sync-policy 自设的 v1.1+ 要求；巡检日志、注册表、plan.md 之间存在相互矛盾的时间线（如 M3 宣称于 04-10 完成，而其前置 #55/#56 任务在 04-13 的 `5798e70` 中仍有收尾）。2026-08-29 的 `f03a3ff` 一次性把文档「刷新到现实」，其中包含把 T-060..T-064 补录进注册表、改写 plan.md 状态行。

**根因**：文档的更新动力来自流程要求（DoD 检查项），流程停摆后文档冻结在停摆日的状态；等到差距过大，只能整体追改。追改本身又破坏了文档作为**过程记录**的价值——它变成了一份不断被重写的「当前状态说明」。

**影响**：新会话（包括 AI 与人）读到的是被追认过的历史，若不经 git 取证无法还原真实时序。文档失去「合同」作用（doc-sync-policy.md 自称的原则），退化为宣传品。

### P8 · 角色 prompt 与维护期工作流冲突

**现象**：`.claude/CLAUDE.md` 与根 `CLAUDE.md` 仍在向**每一个**新会话注入「你是 PM Agent，按 patrol SOP 执行」的构建期角色定义。而维护期的实际工作（gap 分析、写代码、直推 main）与该角色的 Forbidden Actions（不得改 `internal/` 下的 `.go`、不得直推 main）直接冲突。2026-08-29 的三连提交就是在「名义上是 PM、行为上是维护开发者」的错位下发生的。

**根因**：角色定义是为一支**不存在的团队**（6 个开发 Agent + TL + QA）保持在场而写的；团队解散后它没有被退役，反而成了唯一留存的「制度」。

**影响**：轻则每次会话浪费上下文加载无人使用的 SOP；重则以角色之名产生自我矛盾的行为（P4 即其表现）。这也是 2026-04-10 harness 讨论中「角色越界」问题的镜像——当时是 PM 越界改代码，现在是「PM」越界推主干。

## 四、根因抽象

八个问题收敛为四条结构性根因：| # | 根因 | 对应问题 |
|---|------|---------|
| R1 | **约束只存在于 prompt，不存在于基础设施**：Forbidden Action、门禁、「main 只收 PR」全部是文字，没有分支保护、CI 强制或 hook 拦截 | P1、P4 |
| R2 | **正确性信号闭环在系统内部**：评审者、验收者与实现者是同族 LLM，DoD 不含外部锚点（原版行为、真实使用） | P3、P5 |
| R3 | **协调者无状态 + 治理依赖人工触发**：巡检、回填、注册表同步都以「有人开着会话」为前提 | P1、P2、P6 |
| R4 | **文档作为过程记录 vs 状态说明的角色混同**，且缺乏「停止维护即归档」的机制 | P7、P8 |

值得强调：R1–R3 在 2026-04-10 的 harness 设计讨论中已被识别（该讨论提出的 5 层 harness 中，hooks 与 state.json 两层至今物理缺失——`.claude/` 目录下只剩 CLAUDE.md）。**同一个根因被发现了两次，第一次的修复方案没有落地，第二次的表现形式更严重**（从越界改代码升级为无门禁直推主干）。这说明「用文档修复流程问题」本身就会被同一个机制吞掉。

## 五、改进建议

按「下一个多 Agent 项目可直接采用」的优先级排列。原则：**凡是能用基础设施强制的，不放进 prompt；凡是需要持续触发的，不依赖有人在场。**

### 建议 1：把门禁下沉到 git + CI（对应 R1，成本最低，收益最大）

- main 分支开启保护：只收 PR、要求 CI 绿、至少 1 review；
- CI 固化 `make all`（vet + test + build）与 `make docs-check`；
- 增加两个廉价红线指标：`grep -c "TODO(dep)"` 不允许上升；`grep -rc "not yet implemented"` 对外暴露路径不允许新增。
- 本项目当前即可执行：这是纯仓库配置，不触碰代码。

### 建议 2：git 是唯一数据源，注册表要么自动化要么退役（对应 R3）

- 维护期任务的注册表若不与 PR/issue 联动，必然漂移。二选一：(a) 用 label/PR 模板把任务状态表达在 git 事件流上；(b) 明确宣布注册表为**历史归档**，加一行「此后以 git log 为准」的封存说明。
- 本项目建议选 (b)：13 个未登记 PR 已经无法可靠回溯补录，追录（如 T-060..T-064 的做法）只会制造第二套追认历史。

### 建议 3：为「重写/对齐」类项目引入外部 DoD（对应 R2）

- 验收标准至少含一项外部锚点：与原版可执行文件的行为对比清单（哪怕是 20 条核心 CLI 行为）、或真实使用场景的 smoke 脚本；
- 「覆盖率」「测试通过」只证明自洽，不证明对齐。原版二进制是现成的 oracle，弃用它等于放弃了重写项目最便宜的验收基准。

### 建议 4：回填欠账显性化（对应 P6，本项目当务之急）

- 56 个 TODO(dep) 与 42 个桩需要一次**了断**：要么为可见度最高的桩（bootstrap/plugin、bootstrap/mcp、tools/misc）立项排期，要么把对应工具从注册与帮助信息中摘除/标注 experimental，停止以「已实现」面目示人；
- 欠账不可怕，欠账不可见才可怕。

### 建议 5：阶段切换时同步退役角色与流程（对应 R4）

- 构建结束 = 治理文档归档时点。CLAUDE.md 应改写为维护期版本：目标、约束（哪些能直改、哪些必须 PR）、当前欠账清单；
- 本次复盘后续建议的动作之一即起草该维护期版本（另见「后续动作」）。

## 六、与 2026-04-10 Harness 讨论的对照

| 04-10 讨论识别的问题 | 当时方案 | 今日状态（08-29） |
|---|---|---|
| 角色越界（PM 改代码） | 角色 .md + Forbidden Actions | 仍有角色注入，且发生直推 main（P4/P8） |
| 权限/门禁缺口 | 5 层 harness（含 hooks、state.json） | hooks 与 state 持久化两层物理缺失 |
| 状态漂移 | task-registry 唯一数据源 | 注册表停更 4.5 个月，13 个 PR 账外（P2） |
| 上下文丢失（跨会话） | agent-output JSON 协议 | 协议文档在，运行时无人产出/解析 |
| 输出不一致 | 统一输出格式 | 维护期工作完全绕开该协议 |
| 仅靠 prompt 强制 | （该讨论的核心结论） | **验证成立**：所有 prompt 级约束最终都被绕过 |

结论：04-10 的诊断是对的，药方（文档化的 harness）没有执行力。本次复盘不再开新药方，只保留一类：**有技术执行载体的约束**（建议 1、2）。

## 七、本复盘的已知局限

1. **行为层面未验证**：本文只做流程与工件取证，未实际运行两版二进制对比行为。P3 的「≈3.2%/5.3%」是 LOC 粗估，不等于功能覆盖比例（Go 与 TS 表达密度不同；但数量级差距足以支撑结论）。
2. **PR 内容未逐个审阅**：13 个维护期 PR 只从提交粒度归因，未重放每次 diff。
3. **账号与人的映射未知**：tunsuy/marshal 按 git 作者字段统计，未假设同一自然人；责任分析刻意停留在「流程缺口」层面。
4. **单项目样本**：结论适用于「LLM 多 Agent + 人类弱参与」的类似配置，外推需谨慎。
